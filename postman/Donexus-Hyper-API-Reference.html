1  Overview

Donexus exposes the same operator capabilities as its SuperAdmin console to Calcite Hyper: tenants and their admin accounts, plans and features, subscriptions and overrides, billing, support tickets, the leads CRM, the dashboard and the audit log. The console and this API call the same service code, so they cannot disagree. Every request authenticates with a static server-to-server API key sent as x-api-key, compared as a SHA-256 digest in constant time. JWTs are not accepted on these routes.

SystemBase URLKeyScope
Donexus
Charity fundraising		https://ngoplatformbe.onrender.com/api
local: http://localhost:5000/api		dnx_live_…Multi-tenant, one database. Tenant routes address a tenant by :id — the tenant id or its slug.

Every path below is relative to the base URL, e.g. GET {base}/integration/ping. Confirm the production base URL with the Donexus team before go-live.

Configuration

Keys are read from INTEGRATION_API_KEYS — comma-separated name:key pairs; the name is an audit label only and is never secret:

INTEGRATION_API_KEYS=hyper:dnx_live_xxxxx,hyper-old:dnx_live_yyyyy

Changing it needs a redeploy. Two pairs at once make rotation zero-downtime. A pair whose key is shorter than 24 characters is ignored (with a warning), so hyper:test never works. If no valid pair is configured, every integration route returns 503 INTEGRATION_DISABLED — a configuration fault, not an auth failure. Generate a key with:

node -e "console.log('dnx_live_' + require('crypto').randomBytes(32).toString('base64url'))"

Actor attribution

Send the optional x-actor-email: person@calcite.live header with the staff member behind the click. It grants nothing; it names them in the Donexus audit log, where every write through this API is recorded as integration:hyper (person@calcite.live) (or integration:hyper without the header), with meta.reason when a reason is sent.

Response envelope

Everything is wrapped: { "success": true, "data": …, "meta"?: {…}, "warnings"?: [{ "code", "message" }] }, and on failure { "success": false, "error": { "code", "message", "details"? } }. Branch on error.code, not the message. Warnings are non-fatal facts on a successful write (for example STRIPE_CANCEL_FAILED, NOT_BILLED) — show them to staff.

Conventions

Field namessnake_case. Keys inside limits and feature_flags are catalogue codes and pass through verbatim (eventsQuota, adminSeats).
Unknown fieldsRefused with 400 UNKNOWN_FIELD — featureFlags instead of feature_flags fails loudly instead of silently changing nothing.
DatesISO 8601 UTC, or null. Date-only to filters include the whole day.
MoneyNumbers in whole currency units next to a currency (platform-wide AUD).
Billing cyclemonthly | yearly (annual also accepted as input).
Pagination?page=&limit= → meta: { page, limit, total, pages } on tenants (100/500), tickets, leads, invoices (50/200) and audit (100/500). Plans, coupons, admins and the feature matrix return everything.
CachingEvery response is Cache-Control: no-store; reads are live.
Privilege model. The integration key carries full platform-operator access to tenant, plan, billing, support and CRM operations — the same actions as a SuperAdmin console owner, applied immediately with no approval step, and every write is audited. Three things stay in the console: impersonation (act-as is refused), platform operators and platform settings (Team, Stripe/email configuration, email templates), and taking a card during lead conversion.

3  Gotchas

1Merge vs replace. PATCH /plans/:code and PUT /feature-matrix merge per key into limits and feature_flags (keys you omit keep their value; null = unlimited) and pricing per cycle. PUT /tenants/:id/override replaces the whole override — keys you omit fall back to the plan. PATCH /leads/:leadId changes only the fields you send, but a list you send (tags, contacts) replaces the stored list.
2Billing isn't restarted, and some flags don't move money. Suspend and delete cancel the tenant's Stripe subscription, and Stripe cancellations are final: reactivating or restoring doesn't restart billing (BILLING_NOT_RESTARTED). A tenant created with POST /tenants or converted as comped has no Stripe subscription. comp records who pays; an override pricing is for reporting only and doesn't change what Stripe charges — to change a paying tenant's price, fork a plan and assign it.
3Money-moving endpoints. assign-plan on a Stripe-billed tenant swaps the price with prorations (a cycle change resets the billing date). migrate-subscribers with create_prorations or always_invoice charges tenants; always_invoice invoices immediately. There is no dry-run — the API key is enough.
4Price changes are grandfathered. Editing a plan's price mints a new Stripe price; tenants already paying stay on the old one (SUBSCRIBERS_GRANDFATHERED warning) until you call migrate-subscribers.
5Soft deletes and hard deletes. Deleting a tenant sets status deleted and keeps every record; archiving a plan keeps tenants on it; archiving a coupon keeps the record. Permanent: DELETE of a ticket, of a lead, and of a coupon nobody redeemed (a redeemed coupon returns 409 COUPON_REDEEMED).
6Some calls email real people. A ticket comment with is_internal: false (and the first resolve's satisfaction survey), a lead reply, every lead conversion, and an admin password-reset. is_internal defaults to true, so a ticket note is never emailed by omission; a lead reply requires author_name because it signs the email.
7Resolve assignees first. Ticket assignees must be an admin of that tenant — take an id from GET /tenants/:id/admins (404 ASSIGNEE_NOT_IN_TENANT). Lead assignees must be a platform operator — take an id from GET /leads/staff (400 INVALID_ASSIGNEE).
8Tenant admins vs the tenant. /tenants/:id/admins/:userId acts on one person: suspending an admin signs them out but the charity's site and donors carry on. To lock the whole charity, PATCH /tenants/:id { "status": "suspended" }. Nothing here sets or reveals a password.
